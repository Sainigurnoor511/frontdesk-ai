# Design: Auth + Organizations + Dashboard Shell

Date: 2026-08-01
Status: Approved (pending spec review)

## Context

FrontDesk.ai is an open-source AI receptionist platform (see `docs/FrontDesk.ai_Design_Document_Page_1..5.md`). The full platform spans 11 implementation phases (auth, dashboard, AI agents, phone/provider settings, inbound voice pipeline, knowledge base/RAG, calendar, CRM, analytics, integrations/webhooks, testing). This design covers only the **first phase**: Authentication, Organizations, and the Dashboard Shell. It establishes the foundation every later phase builds on (org-scoped data, the page layout AI Agents/Calendar/CRM/etc. will render into).

Repo state at design time: fresh Next.js 16 (App Router) scaffold with shadcn/ui components already vendored into `components/ui/`, no application code, no database, no auth.

**Next.js 16 breaking-change note** (per `AGENTS.md`, verified against `node_modules/next/dist/docs/`):
- Route Handler `context.params` is a `Promise` — must `await params`.
- `GET` Route Handlers are **dynamic by default** (not statically cached) unless opted into `force-static` or wrapped in `use cache`.
- New `RouteContext<'/path'>` global type helper available for typed dynamic segments (generated by `next dev`/`next build`/`next typegen`).

## Scope

In scope:
- Email/password and Google OAuth signup/login via Supabase Auth
- Auto-created organization + owner membership on signup
- `organizations` and `members` tables with RLS, single-org-per-user (no org switcher UI)
- Full dashboard sidebar/header shell per Page 5 UI spec, all nav sections present, most pages placeholder empty-states
- Two real pages beyond Home: Organization settings, User settings
- Local Supabase CLI setup for self-hosting

Out of scope (future sub-projects): AI agents, phone numbers, voice pipeline, knowledge base, calendar integration, CRM/contacts, analytics, integrations/webhooks, multi-org switcher, role management UI, invites.

## Architecture & Auth Flow

- Supabase Auth via `@supabase/ssr`, two providers: email/password and Google OAuth.
- Route groups: `app/(auth)/login`, `app/(auth)/signup` — public. `app/(dashboard)/...` — protected.
- `app/(dashboard)/layout.tsx` is a Server Component: reads session via Supabase server client, redirects to `/login` if absent, fetches the user's org+role server-side (no client fetch waterfall for shell chrome).
- `middleware.ts` refreshes the Supabase session cookie on every request (standard `@supabase/ssr` pattern).
- Signup flow (email/password or Google, first session): a server action creates `organizations` row (name from signup form) + `members` row (role=`owner`) atomically, then redirects to `/`. Google OAuth completes via callback route (`app/(auth)/callback/route.ts`), which runs the same org-creation-if-missing logic on first login.

## Database Schema & RLS

Local Supabase CLI project (`supabase/` dir, migrations under `supabase/migrations/`) so contributors can `supabase start` and self-host.

Tables (this phase only; later phases add more via additive migrations):

```sql
organizations (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  created_at timestamptz not null default now()
)

members (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references organizations(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  role text not null check (role in ('owner', 'admin', 'member')),
  created_at timestamptz not null default now(),
  unique (organization_id, user_id)
)
```

RLS:
- `organizations`: SELECT/UPDATE allowed only if `auth.uid()` has a `members` row for that `organization_id`.
- `members`: SELECT own org's rows only. INSERT/UPDATE **not** granted to the `authenticated` role — org+membership creation happens server-side via the Supabase **service-role** client inside the signup server action, avoiding the chicken-and-egg problem where RLS would block a user from inserting a membership row for an org they aren't a member of yet. The service-role key is server-only, never sent to the browser.

Role field is included now (owner/admin/member) even though there's no invite or role-management UI yet, to avoid a schema migration when that ships later.

## Dashboard Shell & UI

Per Page 5 spec: light mode only, zero custom CSS, default shadcn/ui theme, Tailwind for layout only, Lucide icons.

- `components/layout/app-sidebar.tsx` — shadcn Sidebar block. Sections: Home, Guides; Operations (Calendar, Availability, Clients, Staff, Conversations, Analytics); Receptionist (AI Agents); Setup (Organization, Integrations, Booking Page); General (Settings, More). Bottom: Upgrade Card (default Card component).
- `components/layout/app-header.tsx` — Assistant, Help, Notification buttons + user Avatar dropdown (User Info, Usage Summary, Settings, Dark Mode [disabled/future], Logout).
- Notification bell opens a Popover with an empty state.
- "More" opens a DropdownMenu: AI Assistant, Organization, AI Agents, Settings, Lock Sidebar Layout.
- `components/layout/nav-user.tsx` — avatar dropdown component.
- All sidebar links route to real folders under `app/(dashboard)/...`. Page bodies are empty-state placeholders (Card with icon + "Coming soon") **except**:
  - **Home** — welcome message + org name (real, reads server-fetched org).
  - **Organization settings** — view/edit org name, owner-only edit (real).
  - **Settings** — user profile (name/email), logout (real).
- Responsive behavior comes from shadcn Sidebar's built-in responsive support: fixed sidebar desktop, collapsible tablet, Sheet/drawer mobile. No custom breakpoint code.
- Loading: Skeleton components while the layout fetches org/user server-side. Error: Alert component on fetch failure.

No org-switcher component is built (single-org-per-user for v1).

## Validation, Error Handling, Testing

- Zod schemas for signup (email, password min-length, business name) and org-name-update forms, shared between client (React Hook Form + zodResolver) and re-validated inside the server action.
- Server actions return a typed `{ error }` shape or redirect on success. Inline field errors on forms; Sonner toast for unexpected/unmapped failures.
- Auth errors (invalid credentials, duplicate email, OAuth failure) are mapped to friendly messages — raw Supabase error strings are never shown to the user.
- Testing: no test framework exists yet. This phase adds Vitest (unit tests for Zod schemas and server-action logic against a mocked Supabase client) and a small Playwright smoke suite (signup → dashboard, login → logout) since auth is the highest-risk path in this phase. Exact tooling/config finalized in the implementation plan.
- Accessibility: relies on Radix/shadcn primitives for focus management and ARIA; ensure all form inputs have associated labels.

## Open Questions / Deferred

- Org switcher and invite flow: deferred to a future sub-project once multi-org is needed.
- Role-based UI restrictions beyond "owner can edit org name": deferred until roles beyond owner are actually assignable.
